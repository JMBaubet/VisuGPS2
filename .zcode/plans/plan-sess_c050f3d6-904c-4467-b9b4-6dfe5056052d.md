# Plan — Backend Tauri : points GPX riches + persistance des keyframes

## Périmètre (validé)
1. **Nouvelle commande `get_trace_points`** : renvoie les points GPX complets avec **altitude** et **distance cumulée par point** (calcul 3D Haversine côté Rust, comme `compute_stats`).
2. **Persistance des keyframes** : `save_keyframes`, `get_keyframes`, `delete_keyframes` — **un fichier `keyframes/{trace_id}.json` par trace**, écriture atomique tmp+rename, suppression à la suppression de la trace.
3. **Déclenchement Phase 1** : le bouton « Éditer » ne régénère les keyframes que s'ils n'existent pas déjà (spec §3.1).
4. **État mémoire conservé** : pas de `?trace=` dans l'URL. Le garde-fou (retour accueil si `selectedTraceId` null) reste. La persistance évite surtout de régénérer les keyframes à chaque entrée.

Algorithme de frustum **reporté** (on garde l'échantillonnage régulier côté TS). Aucune nouvelle dépendance Cargo (`serde_json`, `serde`, `uuid` déjà présents). Aucune capability à modifier (I/O Rust-side). Le compte de commandes passe de **20 à 24** (4 nouvelles).

- Nouveau store `src/stores/keyframes.ts` (chargement/sauvegarde des keyframes persistés).
- Modification de `Circuit.vue` (déclenchement : `get_keyframes` → si absent, l'édition les générera et les sauvegardera).
- Modification de `EditionMap.vue` : utiliser les keyframes persistés si présents, sinon générer + sauvegarder.
- Nouveau type miroir `TracePoint` dans `traces.ts` + action `getTracePoints`.

## Détail par fichier

### 1. `src-tauri/src/import_gpx.rs`

#### 1a. Nouveaux structs (miroir exact, snake_case)
```rust
/// Point de trace enrichi (lat, lon, altitude, distance cumulée depuis le départ).
pub struct TracePoint {
    pub lat: f64,
    pub lon: f64,
    pub alt: Option<f64>,
    pub distance_m: f64,   // distance cumulée 3D depuis le départ (m)
}

/// Réponse de get_trace_points.
pub struct TracePoints {   // renvoyé par la commande
    pub id: String,
    pub points: Vec<TracePoint>,
}
```
`TracePoint` et `TracePoints` : `#[derive(serde::Serialize, serde::Deserialize, Clone, Debug)]`.

#### 1b. Nouveau helper `extract_points_with_distance(gpx) -> Result<Vec<TracePoint>, String>`
- Réutilise le pattern de `compute_stats` : itère `gpx.tracks.segments.points`, collecte `(lat, lon, Option<ele>)`.
- Calcule la distance 3D cumulée avec la même formule que `compute_stats` (Haversine via `haversine()` local + `delta_alt`, `dist_3d = sqrt(dist_2d² + delta_alt²)`). Premier point à `distance_m = 0`.
- Ce helper est la **source unique** pour les points riches, réutilisé par la commande `get_trace_points` (et potentiellement le futur frustum).

#### 1c. Commande `get_trace_points(app, trace_id) -> Result<TracePoints, String>`
- `get_mode_dir` → lit `gpx/{filename}` (résolu via `load_registry` pour trouver le `filename` de la trace, comme `rebuild_geometry_from_gpx`).
- Re-parse le GPX, appelle `extract_points_with_distance`.
- **Pas de persistance** (les points sont régénérés à la demande depuis le GPX source — comme le suggère la spec §3.4 : « les points intermédiaires seront chargés depuis le GPX original »).

#### 1d. Persistance keyframes — helpers de chemins
```rust
fn get_keyframes_dir(mode_dir: &Path) -> Result<PathBuf, String>   // mode_dir.join("keyframes"), create_dir_all
fn get_keyframes_path(mode_dir: &Path, trace_id: &str) -> PathBuf   // keyframes/{trace_id}.json
```
(Même patron que `get_gpx_dir` / `get_geojson_path`.)

#### 1e. Commandes keyframes
- `save_keyframes(app, trace_id, keyframes_json) -> Result<(), String>` : `keyframes_json` est une `serde_json::Value` (le `KeyframeSet` sérialisé par le frontend). Écriture atomique tmp+rename (`with_extension("json.tmp")`).
- `get_keyframes(app, trace_id) -> Result<Option<serde_json::Value>, String>` : renvoie le JSON désérialisé si le fichier existe, `None` sinon. (Le frontend reçoit l'objet `KeyframeSet` déjà typé.)
- `delete_keyframes(app, trace_id) -> Result<(), String>` : supprime `keyframes/{trace_id}.json` si présent (ignore l'erreur si absent).

#### 1f. Branchement dans `delete_trace` (existant)
Ajouter `let _ = delete_keyframes_file(&mode_dir, &trace_id);` à côté de la suppression du `.gpx` et `.geojson` — pour ne pas laisser de clé orpheline. (Petit helper interne qui prend `mode_dir` directement, réutilisé par la commande `delete_keyframes`.)

#### 1g. Aucune modif aux signatures existantes
`get_trace_geometry`, `import_gpx_file`, etc. inchangés. Le GeoJSON LineString `[lon,lat]` reste tel quel (non-intrusif pour `Accueil/Map.vue`).

### 4. `src/stores/keyframes.ts` (NOUVEAU)
Pattern Setup Store, wrappe les 3 commandes keyframes :

- `saveKeyframes(set: KeyframeSet): Promise<void>` → `invoke('save_keyframes', { traceId: set.trace_id, keyframesJson: set })`.
- `clearKeyframes(traceId): Promise<void>` → `invoke('delete_keyframes', { traceId })`.

### 5. `src/components/Accueil/Circuit.vue` (déclencheur, spec §3.1)
`editerCircuit()` :
- `editionStore.selectTrace(trace.id)`.
- Tente `keyframesStore.loadKeyframes(trace.id)` :
  - si présent → `editionStore.setKeyframeSet(set)` **sans** regeneration (note : il faudra aussi nourrir la polyligne ; voir §6).
  - si absent → on navigue ; `EditionMap` générera et sauvegardera.
- `router.push({ name: 'editionCamera' })`.

Pour la polyligne du marker : on garde la génération côté TS à partir de la géométrie LineString (déjà en place via `buildTracePolyline`). `setKeyframeSet(set, feature)` reste la voie d'entrée ; quand les keyframes viennent du disque, on passe quand même la `feature` (chargée par `EditionMap` via `getTraceGeometry`), la polyligne est donc toujours disponible. Cohérent.

### 6. `src/components/Edition/EditionMap.vue`
Après `getTraceGeometry` + `generateKeyframes`, remplacer le flux par :
1. Charger la `feature` (existant).
2. `const persisted = await keyframesStore.loadKeyframes(traceId)`.
3. Si `persisted` → `editionStore.setKeyframeSet(persisted, feature)` (pas de régénération).
4. Sinon → `const kf = generateKeyframes(traceId, feature); editionStore.setKeyframeSet(kf, feature); await keyframesStore.saveKeyframes(kf)`.
5. Le reste (marker, rAF, fitBounds) inchangé.

## Points techniques / risques
- **Re-parsing GPX** pour `get_trace_points` : on relit le `.gpx` source à chaque appel. Acceptable (les points ne sont demandés qu'à l'entrée en édition). Si perf nécessaire plus tard, on pourrait persister `{trace_id}.points.json` à l'import. Pas dans ce scope.
- **`delete_trace` cascade** : bien ajouter la suppression `keyframes/` pour éviter un fichier orphelin.
- **Compteur de commandes** : 20 → 24. À propager dans `COMMANDS.md`, `CLAUDE-CODE-GUIDE.md`, `README.md`.
- **Arborescence de stockage** : nouveau dossier `keyframes/` à documenter dans `DATA_STORAGE.md`.
- **Miroir des types** : `TracePoint` et `KeyframeSet` doivent correspondre exactement (snake_case) entre Rust et TS. Le `KeyframeSet` Rust est transparent (`serde_json::Value`), donc pas de struct Rust à maintenir pour ça — le contrat est le type TS `KeyframeSet` (déjà défini dans `keyframeGenerator.ts`, conforme spec §3.4).
- **Validation du JSON persisté** : `loadKeyframes` vérifie `trace_id` + `keyframes` non vides ; en cas de forme invalide, on log + on régénère (robuste).

## Validation
1. `cargo build` (Tauri) compile sans erreur ni warning nouveau.
2. `npm run build` (vue-tsc + Vite) passe.
3. Entrer en édition la 1re fois → génère + **sauvegarde** `keyframes/{id}.json` (vérifiable sous `{app_data_dir}/{mode}/keyframes/`).
4. Sortir puis ré-entrer → charge le JSON sans régénérer (le `total_duration_ms` est identique, pas de flicker de génération).
5. `get_trace_points` renvoie bien altitudes et distances cumulées (vérifiable via un `console.log` temporaire ou le HUD futur).
6. Supprimer la trace → `keyframes/{id}.json` disparaît aussi.
